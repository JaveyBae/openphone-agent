# 答辩提纲（30 分钟）

## 1. 问题怎么理解（2 分钟）
- 难点不是“让模型点手机”，而是**同一台手机、同一时间、两个使用者**：手机从输入、焦点到键盘都假设只有一个人。
- 因此先解决“Agent 在哪里操作”，再解决“Agent 怎么决定操作”。

## 2. 关键决策：后台独立显示屏（5 分钟）
- 方案对比见 README“为什么这样做”。核心论点：只有“同一台设备上的第二块逻辑屏幕”同时满足“不打扰”和“结果落在用户自己的 App/账号”。
- Android 15 的 `OWN_FOCUS` + `STEAL_TOP_FOCUS_DISABLED`：后台屏有自己的焦点，App 在上面不会抢主屏焦点；用 shell 身份（ADB 授权，非 Root）创建。
- 走过的弯路（有证据）：MediaProjection 的显示屏没有独立焦点，2026-10-04 的回归里两次 Back 把全局焦点从 0 切到了后台屏 → 换成 shell 创建的可信屏（docs/workspace-isolation.md）。
- 原则：**fail closed**。焦点不对就停，不做“自动切回来”的掩盖。

## 3. 现场演示（5 分钟）
按 docs/DEMO.md：用户在主屏刷网页打字，Agent 在后台屏用经验模式新建联系人，最后展示核对结果和 owner_observer 报告。

## 4. 是 Agent 不是脚本：经验模式（5 分钟）
- 纯 Agent：每一步 9B 看截图决定。
- 经验：只从**核对通过的模型真实运行**学，删绕路，分“结构 / 内容 / 提交”，复用时逐步比对实时屏幕；内容、提交、陌生页面永远交给模型。
- 数据：同类联系人任务，纯 Agent 123 s / 18 次模型调用 → 经验模式 83.6 s / 7 次。
- 自我反思：最早做的“技能”是我（和 AI）手写的固定流程，本质是脚本；意识到这一点后推倒重来，改为从真实轨迹学习，旧技能保留为 `legacy` 只做对比。

## 5. “说办好了就是真办好了”（3 分钟）
- 真实案例：模型只填了两项就保存，却声称五项都存了 → 完成核对在通讯录里找不到邮箱电话，没有当作完成。
- 闭环：执行 → 核对 → 把缺失项反馈给模型自我纠正 → 仍缺则交给用户。核对通过才学经验。

## 6. 让 9B 小模型更稳的工程手段（3 分钟）
- 把事实反馈给模型：输入框已聚焦（后台屏没键盘）、上一步没改变屏幕、在打转、App 没装、核对缺项。
- 输出容错：多动作只执行第一个；“动作 + 完成”只执行动作；空输出/坏引号重问一次；输出上限 768 token（曾因模型啰嗦写满 2048 token，单步 37 秒）。
- 每个改动都来自一次真实失败的运行记录（runs/ 下有截图和原始输出）。

## 7. 安全与交接（2 分钟）
- 草稿不发送、整页检查（下单/付款/协议/登录/Cookie）、权限弹窗不代选、随时“接管到主屏”。
- 同 App 冲突：用户和 Agent 同时打开同一个 App 时 Android 会把任务移给用户 → 停下，不关闭用户窗口；只有用户点按钮才关闭主屏那个窗口。
- 真实教训：一次调试中我（开发者）误把用户刚打开的京东窗口关掉了。之后把规则写死：发现同 App 冲突只提示，不做任何关闭。

## 8. 普通手机怎么落地（2 分钟）
- 需要 Android 15+ 和一次 ADB 授权（无线调试配对即可），不需要 Root。
- 路线：Shizuku 式本机 shell 服务替代电脑端 → 手机独立运行；模型可云端可端侧。
- 风险：部分 ROM 限制 shell 创建可信显示屏（会安全失败）；国内 App 在模拟器上风控严。

## 9. 局限与下一步（1 分钟）
- 跨 App 串联：9B 会跳步 → “先拆任务再逐步执行”的规划层。
- 提速：操作后的固定 1 秒等待改为“屏幕稳定即继续”；界面读取与模型推理并行。
- 手机本地化服务。

## 如何与 AI 协作开发
- **我定方向和边界，AI 实现**：例如“不能抢用户窗口”“结果必须可验证”“经验要从真实轨迹学”都是我提出并坚持的约束，写进 CLAUDE.md 让每次会话遵守。
- **审查 AI 的产出**：AI 一度把“手写技能”包装成“学会的技能”——我指出这其实是脚本，要求改为从模型轨迹学习；AI 写的经验学习第一版有两个 bug（误删正常步骤、“Phone”被当成请求里的值），是通过检查学到的经验发现并修复的。
- **用真实运行验证，而不是只看单元测试**：200+ 单元测试之外，每个功能都在模拟器上真机跑过；失败的运行保留截图和模型原始输出，作为下一步改进的依据。
- **AI 犯过的错也是素材**：误执行 `adb root` 导致后台屏被销毁；误关用户的京东窗口。都已修正并转成规则。

## 可能被问到的问题
- **为什么不用无障碍服务直接点？** 无障碍手势落在主屏，会和用户抢；后台屏是独立焦点的显示屏，输入定向到它。
- **后台屏的 App 会不会弹到前台？** 有独立焦点且禁止抢顶层焦点；每步都核对，一旦发现在主屏就停（京东同时被用户打开时就触发过）。
- **为什么不用更大的模型？** 9B 端侧可部署、延迟低；用工程手段（反馈、容错、核对、经验）把小模型做稳；规划层可以接更强的模型。
- **经验会不会学错？** 只学核对通过的运行；复用时每一步都要求屏幕一致且控件存在；内容和提交步骤永远由模型决定。
- **怎么保证不发出消息、不付款？** 控件级白名单/黑名单 + 整页文字检查，在执行前拦截；拦截后不重试、不绕路。
