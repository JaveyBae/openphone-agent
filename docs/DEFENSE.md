# 答辩提纲（30 分钟）

材料：[README](../README.md) · [演示视频（YouTube）](https://www.youtube.com/watch?v=2Jtdmli2-1E) · [隔离设计](workspace-isolation.md) · [录制说明](DEMO.md)

## 1. 问题怎么理解（2 分钟）
- 难点不是“让模型点手机”，而是**同一台手机、同一时间、两个使用者**。手机的输入、焦点、键盘都默认只有一个人在用。
- 所以先解决“Agent 在哪里操作”，再解决“Agent 怎么决定操作”，最后解决“怎么证明它真的做对了”。

## 2. 关键决策：后台独立显示屏（4 分钟）
- 方案对比见 README“为什么这样做”。核心论点：只有“同一台设备上的第二块逻辑屏幕”，能同时做到“不打扰用户”和“结果落在用户自己的 App 和账号里”。
- Android 15 的 `OWN_FOCUS` + `STEAL_TOP_FOCUS_DISABLED`：后台屏有自己的焦点，App 在上面运行不会抢主屏焦点。这块屏用 shell 身份创建，只需要 ADB 授权，不需要 Root。
- 走过的弯路（有证据）：MediaProjection 创建的显示屏没有独立焦点。2026-10-04 的回归测试里，两次 Back 就把全局焦点从主屏切到了后台屏，于是换成 shell 创建的可信屏（见 workspace-isolation.md）。
- 原则：**fail closed**。焦点不对就停，不做“自动切回来”这种掩盖。
- **安全规则也要定义准确**（10-19 真机发现）：用户在主屏打开最近任务（Overview）时，后台任务被误停了。查焦点日志发现，这时主屏只是**暂时没有焦点窗口**，全局焦点其实一直在主屏。规则因此改成：“全局焦点必须在主屏”是底线，“主屏暂时没有焦点窗口”属于用户在正常用手机。Python 和安卓端两处检查都同步改了，并补了测试。

## 3. 演示（5 分钟）
- 先放 2 分钟视频（有中文字幕，讲解每一步的工作逻辑）：
  - 任务一：12306 查 10 月 22 日上海→北京最早一班高铁，用时 72 秒。模型发现 12306 默认日期不对，自己改了日期，回答 G532 06:31 并附各席位票价。
  - 任务二：一句口语“就说文档我看完了，没什么问题，可以往下推了”。模型自拟主题、写好草稿后停下，用户「接管到主屏」后自己决定是否发送。
  - 录制过程中用户一直在主屏刷 Chrome、打字。
- 现场再跑一个（按 DEMO.md）：查火车票最快、最稳（27B 5/5，平均 43 秒）。备选：定闹钟（5/5，38 秒）。
- 演示后展示：App 里的执行过程（哪些步骤按经验执行）、`runs/` 下的逐步截图和模型原始输出。

## 4. 模型选型：从 9B 换到 27B，用数据说话（4 分钟）
- 正式测试：4 个任务，每个配置跑 5 次，用独立方式核对结果（读系统闹钟列表、通讯录界面、日历数据库，12306 结果与页面比对）。

  | 任务 | 9B 纯 Agent | 9B 经验模式 | 27B 纯 Agent | 27B 经验模式 |
  |---|---|---|---|---|
  | 定闹钟 | 5/5 | 5/5 | 5/5（38 s） | 5/5（28 s） |
  | 新建联系人 | 1/5 | 5/5 | 5/5（92 s） | 5/5（55 s） |
  | 建日程 | 2/5 | — | 4/5（86 s） | 5/5（47 s） |
  | 12306 查车次 | 3/5 | — | 5/5（43 s） | 5/5（28 s） |
  | 合计 | 11/20 | 10/10 | 19/20 | **20/20** |

- 离线逐步评测（58 个真实截图步骤）：27B 做对 77.6%，9B 做对 62.1%。
- 结论：默认用 27B 加经验模式，20/20，比纯 Agent 快约 40%。9B 加经验模式也能把联系人任务做到 5/5，所以端侧部署小模型仍然可行。
- 要说清楚：经验模式测的是“同类任务重复做”，这正是它要解决的场景，不代表任意新任务都能 100%。换一种说法、多一个字段时（例如带地点的日程），仍然要靠模型多走几步。
- 测试本身也要被验证：核对脚本的第一版有 bug。比如系统闹钟服务只登记“下一个”闹钟，导致误判失败；改成读时钟 App 里的闹钟开关后才准。修完 bug 后，失败的那几次都重跑了。
- **为什么不直接用 Claude**：试过让 Claude 当规划模型，日程任务一次做对，但每步要等十几秒到几十秒，成本也高。所以把它用作**教师模型**：
  - 给 27B 的真实轨迹逐步标注正确动作，生成 SFT 数据（491 条，`scripts/teacher_dataset.py`）；
  - 亲自演示一遍日程任务，这条轨迹被学成经验。
  - 下一步：用这批数据对 27B 做 LoRA 微调。

## 5. 是 Agent 不是脚本：经验模式（3 分钟）
- 纯 Agent：每一步都由模型看截图决定。
- 经验：只从**核对通过的模型真实运行**里学。先删掉绕路，再把步骤分成“结构 / 内容 / 提交”三类。复用时逐步比对实时屏幕；内容、提交和陌生页面永远交给模型。
- 数据：同类联系人任务，纯 Agent 123 秒、18 次模型调用；经验模式 83.6 秒、7 次。
- 10-19 的改进：经验原来按句子的相似度来匹配，“加一个……需求评审会，地点……”和示范句子“建一个……会议，叫……”相似度只有 0.38，经验没被用上。现在改为按**任务类型**匹配（日历新建、闹钟、联系人），换个说法也能用上。
- 自我反思：最早做的“技能”是我（和 AI）手写的固定流程，本质上就是脚本。意识到这一点后推倒重来，改成从真实轨迹学习；旧技能保留为 `legacy` 模式，只用来对比。

## 6. “说办好了就是真办好了”（2 分钟）
- 真实案例：模型只填了两项就点了保存，却声称五项都存好了。完成核对在通讯录里找不到邮箱和电话，没有把它当作完成。
- 日程核对会去系统日历数据库里读回：标题、日期、起止时间（按设备时区计算）都要对上，请求里提到的地点也要对上。
- 核对本身也出过漏洞：“……的需求评审会，地点……”这种说法解析不出会议名，结果这一次根本没去核对，被当成了完成。已经修复，并补了测试。
- 闭环：执行 → 核对 → 把缺失项反馈给模型自我纠正 → 仍然缺就交给用户。只有核对通过的运行才会被学成经验。

## 7. 让模型更稳的工程手段（4 分钟）
原则：**把界面上读得到的事实告诉模型，别让它猜。** 下面每一条都来自一次真实失败的运行。
- **反复点输入框**：后台屏没有键盘也没有光标，模型以为没点中。最初的反馈说“输入框已选中，如果是对的输入框就直接输入”，27B 照样继续点。把同一张截图拿来对比不同措辞：点名是哪个输入框，并明确“不要再点，下一步就是输入”之后，模型才改成输入。
- **日历时间弹窗分不清开始还是结束**：27B 曾在“点开始时间 ↔ 点确定”之间来回交替 22 步。现在会告诉它“这个弹窗设的是开始时间，当前显示 3:30 PM”，以及表单里现在填了什么；两个动作来回交替 3 轮就提前停下，交给用户。
- **地点没存上**：日历地点页给的候选都是不相关的真实地名，按返回键会把输入的文字丢掉，必须按回车。于是给 27B 加了“回车”动作，地点页会提示它。
- **“明天”是哪天**：提示词里加上今天的日期。12306 用北京时间，所以演示时任务里直接写具体日期。
- **输出格式**：例如没给元素列表时，模型却按元素编号点击。现在告诉模型错在哪、让它重答一次，不再直接终止任务。
- **设备端的坑**：读界面的程序出错后没关闭，一直占着系统唯一的 UiAutomation 连接，导致 Gmail 安全检查失败。现在出错时一定会关闭。

## 8. 安全与交接（2 分钟）
- 短信、邮件只写草稿；下单、付款、协议、登录、Cookie 页面整页拦截；系统权限弹窗不替用户选；随时可以“接管到主屏”。
- 遇到人脸识别、风控验证时**不绕过**，停下来交给用户。
- 接管之后 Agent 不再碰那个 App：窗口已经交到用户的主屏上，Agent 只操作后台屏。
- 同 App 冲突：用户和 Agent 同时打开同一个 App 时，Android 会把任务移给用户。这时 Agent 停下，不关闭用户的窗口；只有用户点了按钮，才会关闭主屏上那个窗口。
- 真实教训：一次调试中，我（开发者）误把用户刚打开的京东窗口关掉了。之后把规则写死：发现同 App 冲突只提示，不做任何关闭。

## 9. 普通手机怎么落地（1 分钟）
- 需要 Android 15+ 和一次 ADB 授权（用无线调试配对即可），不需要 Root。
- 路线：用 Shizuku 式的本机 shell 服务替代电脑端，让手机独立运行；模型可以放在云端，也可以放在端侧（9B 加经验模式）。
- 风险：部分 ROM 不允许 shell 创建可信显示屏（这时会安全失败）；国内 App 在模拟器上风控很严。

## 10. 局限与下一步（1 分钟）
- **速度**：27B 每步 2–10 秒，取决于到 GPU 服务器的网络。带地点的日程要 4–5 分钟。网络断开时任务会如实停下。
- **泛化**：经验模式在固定的 4 类任务上 20/20，但新类型的任务、换说法后多出来的字段，仍然要靠模型从头摸索，速度会慢很多（带地点的日程要 4–5 分钟）。
- **下一步**：
  - 用教师数据对 27B 做 LoRA 微调；
  - “先拆任务再逐步执行”的规划层，用于跨 App 任务；
  - 屏幕一稳定就继续，取代固定等待；
  - 手机本地化服务。

## 如何与 AI 协作开发
- **我定方向和边界，AI 负责实现**：“不能抢用户窗口”“结果必须可验证”“经验要从真实轨迹学”，都是我提出并坚持的约束，写进项目的 AI 工作约定，让每次会话都遵守。
- **审查 AI 的产出**：
  - AI 一度把“手写技能”包装成“学会的技能”，我指出这其实是脚本，要求改成从模型轨迹学习；
  - AI 写的经验学习第一版有两个 bug（误删正常步骤、把“Phone”当成请求里的值），是检查学出来的经验时发现并修复的。
- **在真实 App 里验证，不只看单元测试**：239 个单元测试之外，每个功能都在模拟器上实际跑过。10-19 我要求“必须在 OpenPhone App 上验证”，结果暴露出 Overview 误停、读取程序没关闭、安卓端焦点检查过严、模型输出格式等 6 个单元测试没覆盖的问题，都已经修复。
- **要求给出证据**：AI 曾把一次失败归因于“主屏窗口重建”，对照焦点日志后发现那次窗口变化发生在失败之后 3 秒，结论被推翻。之后的排查都要求附上时间线和日志。
- **AI 犯过的错也是素材**：误执行 `adb root`，导致后台屏被销毁；误关用户的京东窗口。都已修正并写成规则。

## 可能被问到的问题
- **为什么不用无障碍服务直接点？** 无障碍手势落在主屏，会和用户抢；后台屏是有独立焦点的显示屏，输入定向发给它。
- **后台屏的 App 会不会弹到前台？** 后台屏有独立焦点，并且禁止抢顶层焦点。每一步都会核对，一旦发现全局焦点离开主屏就停（用户同时打开京东时就触发过）。
- **为什么是 27B 而不是 9B？** 正式测试 19/20 对 11/20，离线评测每步正确率 77.6% 对 62.1%。9B 加经验模式能补上一部分差距，适合端侧部署。
- **为什么不直接用 Claude 或 GPT？** 能做对，但慢、贵，而且截图要发给第三方。它更适合当教师模型：标注数据、示范轨迹，用来提升自己部署的 27B。
- **经验会不会学错？** 只学核对通过的运行。复用时每一步都要求屏幕一致、控件存在；内容和提交步骤永远由模型决定。学错的经验可以挪走，比如一次时间设错的日程轨迹就被移出了经验库。
- **怎么保证不发消息、不付款？** 执行前用控件级的白名单/黑名单加整页文字检查拦截，拦下后不重试、不绕路。邮件写完就停在草稿，由用户接管后自己发送。
- **隐私怎么处理？** 模型只能看到后台屏截图，看不到主屏；截图只发到自己部署的 GPU 服务器。运行记录和经验只存在本地，不进仓库；演示视频里的收件箱已打码。
